### Question 1

Which functions will be called to communicate with a client in your HTTP server code in Part 1?

- [ ] `write_http_response()` followed by `read_http_request()`
- [X] `read_http_request()` followed by `write_http_response()`
- [ ] `write_http_request()` followed by `read_http_response()`
- [ ] `read_http_response()` followed by `write_http_request()`

> **Why:** Spec, "Main Server Loop": step 1 is "Call the `read_http_request()` function ... to read the client's HTTP request", step 3 "Call `write_http_response()` ..., providing the full path to the resource". `http.h` declares exactly these two. `read_http_response()` appears in the spec only as a function in the HTTP lab's client code.

### Question 2

How can you write C code to check if a system call failed specifically because it was interrupted by a signal?

- [ ] Trick question: This is impossible.
- [ ] Make a call to `pause()` immediately after the system call in your code.
- [ ] Check if `errno != EINTR`.
- [X] Check if `errno == EINTR`.

> **Why:** Spec, Hints under "Completing http_server.c": "If `accept()` was interrupted by a signal, it will return `-1` and set `errno` to `EINTR`." `errno != EINTR` is the test for a real failure.

### Question 3

Why might you see an error message like `address already in use` from the `bind()` system call?

- [ ] A process from another user (assuming you are on a shared machine) is currently using the port you tried to bind to.
- [ ] You had a process using this port recently, and the OS linger period for that port has not yet expired.
- [ ] You currently have another process running that is already bound to the port.
- [X] All of the above

> **Why:** Spec, "Port Reservation Issues": "Only one process on a particular computer may bind to a port at a time", which covers your own process and another user's on a shared machine. A closed server socket's port "may not be used for a new socket until this timeout expires" (the *linger period*). "Tests and Ports" repeats both causes.

### Question 4

Which of the following is an example of the text one might see in the first line of an HTTP request?

- [ ] `HTTP/1.0 /index.html GET`
- [X] `GET /index.html HTTP/1.0`
- [ ] `/index.html GET HTTP/1.0`
- [ ] `I Can Has Cheezburger?`

> **Why:** Spec, "Reading HTTP Requests": the request line holds "the operation to perform (method), a resource name, and a protocol version", in that order. The example is `GET /quote.txt HTTP/1.0\r\n`.

### Question 5

Which of the following is true about the strings sent and received by HTTP servers and clients?

- [ ] There is no need to include a null terminator character.
- [ ] Line endings are `\r\n` instead of `\n`
- [ ] Response bodies with text should use whichever line ending was used in the original content being sent to the client.
- [X] All of the above

> **Why:** Spec, "Reading HTTP Requests": "in HTTP, line endings are denoted by the character sequence `\r\n`". "Writing HTTP Responses": the `\r\n` rules "only apply to the status line, response headers, and empty line ... The response body should contain the file's contents *exactly as they are stored on disk*." The spec never mentions a null terminator outright: none of its example messages has one, and `Content-Length` counts only the file's bytes, so a `\0` written after the headers would become the first byte of the body.

### Question 6

What is the difference between the `resource_name` string generated by `read_http_request()` and the `resource_path` string expected by `write_http_response()`? Hint: Consult `http.h`.

- [ ] Trick question: There is no difference.
- [ ] `resource_name` will be null-terminated, while `resource_path` should not be null-terminated.
- [ ] `resource_path` is the name of the resource requested by the client (e.g., `/quote.txt`) while `resource_name` is a path to the corresponding file on the server's local file system (e.g., `server_files/quote.txt`).
- [X] `resource_name` is the name of the resource requested by the client (e.g., `/quote.txt`) while `resource_path` is a path to the corresponding file on the server's local file system (e.g., `server_files/quote.txt`).

> **Why:** `http.h`: `read_http_request()` sets `resource_name` to "the name of the requested resource", and `write_http_response()` takes `resource_path`, "The path to the requested resource in the server's file system". Spec, "Main Server Loop" step 2: resource `/quote.txt` with directory `server_files` maps to `server_files/quote.txt`.

### Question 7

Which of the following is true about the `strtok()` function?

- [ ] It is not re-entrant and therefore not safe for concurrent use by multiple threads.
- [ ] It is called multiple times to return multiple results.
- [ ] It will modify the original string that is tokenized.
- [X] All of the above

> **Why:** Spec, Hints under "Reading HTTP Requests": "`strtok()` will modify the string being tokenized, and subsequent calls to `strtok()` will modify the strings returned from previous calls. Additionally, `strtok()` is not safe to be used from multiple threads. You can use the re-entrant variant" (`strtok_r()`). Each call returns the next token (`man 3 strtok`), hence multiple calls.

### Question 8

When must an HTTP response include a `Content-Length` header?

- [ ] When returning `200 OK` response with data for the client.
- [ ] When returning a `404 Not Found` response to inform the client that the requested resource does not exist.
- [ ] When returning a `200` response but not a `404` response.
- [X] When returning either a `200` response or a `404` response.

> **Why:** Spec, "Writing HTTP Responses": responses "**must always contain two response headers for `200 OK` responses**" (`Content-Length` and `Content-Type`), and "A `404 Not Found` response should contain the `Content-Length` header with a value of `0`." The first two choices are each true but incomplete; the third contradicts the 404 rule.

### Question 9

Say a connection queue contains 0 elements and we call `connection_queue_dequeue()`. What should happen?

- [ ] The function returns an error.
- [ ] The function returns `NULL`.
- [X] The function blocks until an item is added to the queue, and the item is then returned.
- [ ] The function blocks until an item is removed from the queue, and a new item is added.

> **Why:** Spec, `connection_queue_dequeue()`: "If the queue is empty ..., then this function blocks the calling thread until a new element is added to the queue." `connection_queue.h`: it "Returns the removed socket file descriptor on success".

### Question 10

Say a connection queue contains 0 elements and we call `connection_queue_enqueue()`. What should happen?

- [ ] The function returns an error.
- [ ] The function returns `NULL`.
- [ ] The function blocks until an item is removed from the queue, and a new item is added.
- [X] A new item is added to the queue.

> **Why:** `CAPACITY` is 5 (`connection_queue.h`), so an empty queue has room. Spec, `connection_queue_enqueue()` blocks only "If the queue is already full"; otherwise the element is added, and since the queue was empty, "one thread waiting to dequeue is unblocked".

### Question 11

Say a connection queue is filled to its capacity and we call `connection_queue_dequeue()`. What should happen?

- [ ] The function returns an error.
- [ ] The function returns `NULL`.
- [X] A new item is removed from the queue and returned to the caller.
- [ ] The function blocks until an item is added to the queue, and the new item is then returned.

> **Why:** Spec, `connection_queue_dequeue()` blocks only "If the queue is empty". On a full queue it removes and returns an element, and "If this operation frees up a slot in what was a full queue, one thread waiting to enqueue is unblocked." (The queue is FIFO, so the item returned is the oldest, not a "new" one, but this is the only choice that neither blocks nor fails.)

### Question 12

Say a connection queue is filled to its capacity and we call `connection_queue_enqueue()`. What should happen?

- [ ] The function returns an error.
- [ ] The function returns `NULL`.
- [ ] A new item is removed from the queue and returned to the caller.
- [X] The function blocks until space opens up in the queue, at which point the new item is added to the queue.

> **Why:** Spec, `connection_queue_enqueue()`: "If the queue is already full ..., then this function blocks the calling thread until space becomes available, at which point the new element is added to the queue."

### Question 16

Which ports will `make test` attempt to use for the server tests by default?

- [ ] Ports starting at `80`
- [ ] Ports starting at `443`
- [ ] Ports starting at `8080`
- [X] Ports starting at `8000`

> **Why:** Spec, "Tests and Ports": "By default, the `make test` target will start your `http_server` program and instruct it to bind to port `8000` for the first test, and then port `8001` for the second test." `part1/Makefile` and `part2/Makefile`: `port_base ?= 8000`. Caveat (a starter-code bug, seen with `make -n test`): the top-level `Makefile` computes the Part 2 base from `$(primary_port)`, which it never defines, so a top-level `make test` runs Part 2 on ports 3 and 4 whatever `port_base` is. `make test` inside `part2/` uses 8000 and 8001 as documented.

### Question 17

You can change the starting point of the range of ports used by the tests to avoid `bind()` errors. Which of the following will cause tests to run using port numbers starting at `9001`?

- [ ] `make test server_port=9001`
- [X] `make test port_base=9001`
- [ ] `make port_base=9001 test`
- [ ] `make server_port=9001 test`

> **Why:** Spec, "Tests and Ports": "The `test` target accepts an optional `port_base` argument", with the example `make test port_base=4061`. No Makefile has a `server_port` variable. Caveat: GNU make accepts `VAR=value` arguments anywhere on the command line, so `make port_base=9001 test` works too (`make -n port_base=9001 test` in `part1/` gives `PORT1=9001 PORT2=9002`). Choice 2 matches the spec's form, so it's the likely key.

### Question 19

Say your Python HTTP server receives `SIGINT` while it is in the middle of a blocking system call. When will the handler for this signal type execute?

- [ ] Immediately upon receipt of the signal
- [ ] Trick question: Python programs cannot run custom signal handlers
- [X] When control returns to the Python interpreter, i.e., after the system call returns, and potentially never if the system call blocks forever.
- [ ] After some finite delay, the next time the Python interpreter polls for pending signals.

> **Why:** Spec, "Python Signal Handling": "Python doesn't deliver signals immediately to your code when it is in the middle of a blocking system call like `accept`. Instead, it only delivers them once the system call returns." Caveat: on Python 3.10 (the container) and 3.13, a handler installed with `signal.signal` ran at t=1.00s, the moment `SIGINT` arrived while the main thread was in `accept()`, and `accept()` was still blocked 2 s later. That fits PEP 475: the signal interrupts the system call, CPython runs the handler, then retries `accept()`. The spec's practical point holds (the loop never gets past `accept`, hence `settimeout`), but the handler itself isn't delayed. Choice 3 is the spec's wording, so it's the likely key.
